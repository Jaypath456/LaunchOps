# Reproducing the chaos campaign

From the repository root, run `bash scripts/chaos/run.sh` with Docker Compose and Python available. Configure `HIRES`, `REPLICAS`, `KILL_EVERY`, `PAUSE_EVERY`, `PAUSE_FOR`, `LATENCY_MS`, `TIMEOUT`, `ERROR_RATE`, `HANG_RATE`, `DROP_RATE`, and `RUN_ID` through the environment. Defaults are defined in the runner. Set `CHAOS_EVIDENCE` to a new absolute directory under `/tmp` for tooling checks that must not create repository evidence.

`PAUSE_EVERY` is the interval in seconds between attempts to freeze a random running provisioner container; it defaults to off. `PAUSE_FOR` is the freeze duration in seconds. Its default is the provisioner's `LEASE` plus a recovery margin, as defined in the runner. `LEASE` accepts a Go duration and is passed to the provisioner. Pauses overlap the kill loop and each other's waiting periods. An expired lease can be reclaimed while its old worker is frozen; when that worker resumes, its stale finish can exercise fencing. A kill can interrupt this scenario, so fault coverage remains dependent on the observed run.

`LATENCY_MS` sets a fixed simulator delay in integer milliseconds, defaults to disabled, and is applied through `/admin/faults` alongside the rate faults. The delay happens before account or idempotency state changes and stops when the client disconnects. `/admin/stats` reports `latency_fired`, including delays cancelled by a client. Choose latency below the provisioner's call timeout when successful calls need to remain in flight long enough to freeze.

The runner builds an isolated Compose project named `launchops-chaos`, seeds local demo users and distinct chaos employees, enables simulator faults, and creates hires through the authenticated HR API. It includes the standard seeded demo workflow when waiting for all provisioning jobs to reach terminal states. It never uses the frontend. Do not run campaigns concurrently under this project name.

Each invocation selects a fresh MongoDB volume with a random suffix and records its name in `config.json`. Retained volumes from earlier invocations do not block a repeated run identifier when its evidence directory is absent. Existing containers, evidence directories, and campaign volumes are never reused. Containers are stopped and removed on exit with Compose `down`; volumes are retained. Choose a new run identifier to preserve earlier evidence when repeating a campaign. No published ports are needed.

The run directory contains the exact invocation, environment versions, configuration, API creation manifest, read-only job snapshot, simulator accounts and statistics, applied faults, successful kill records, `pauses.jsonl`, provisioner logs, and verification result. Configuration records both pause settings and latency. Each pause records its container, start time, and end time; an unfinished pause fails verification. Exit cleanup stops fault injection and unpauses workers before draining them and before Compose teardown, including on interruption. Killed or removed containers are treated as no longer paused. All measurements are generated by the run. Inspect `verify.json` for invariant failures and dead jobs whose simulator accounts exist and require an IT override. To repeat verification without services, run `python scripts/chaos/verify.py docs/evidence/chaos/<run-id>`.

Full campaign verification requires replay, process kill, and committed-response-drop observations. Fence rejection is required only when a pause was recorded; without pauses, verification explicitly reports it as not required. Pause and latency counts are reported without requiring either fault to be enabled. Missing required observations fail the campaign's `passed` result. Random fault injection may leave a required observation absent even when all jobs terminate correctly.

Setting both `KILL_EVERY=0` and `PAUSE_EVERY=0` selects an explicit tooling dry run. The verifier still records campaign failures and keeps `passed` false when required fault coverage is missing. It additionally records `dry_run_passed`, which requires every job, account, manifest, and pause-completion invariant to pass. Only this explicit mode allows the runner to exit successfully despite missing fault observations; malformed evidence, data invariant failures, and command failures still produce a nonzero exit. The runner waits for every job to become terminal, including jobs awaiting a frozen worker's lease expiry, within `TIMEOUT`. A successful dry run cannot establish the full chaos claim. Repeat its tooling check offline by adding `--dry-run` to the verifier command; without that flag, verification always uses the strict campaign exit status.

This is a local demo on a single host. Accounts, payroll, identity, and devices are simulated; external systems are a local mock with injected faults. These runs make no production, high availability, or failover claim. The browser walkthrough remains manual.

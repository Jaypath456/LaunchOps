# Reproducing the chaos campaign

From the repository root, run `bash scripts/chaos/run.sh` with Docker Compose and Python available. Configure `HIRES`, `REPLICAS`, `KILL_EVERY`, `TIMEOUT`, `ERROR_RATE`, `HANG_RATE`, `DROP_RATE`, and `RUN_ID` through the environment. Defaults and the setting that disables process kills for a dry run are defined in the runner.

The runner builds an isolated Compose project named `launchops-chaos`, seeds local demo users and distinct chaos employees, enables simulator faults, and creates hires through the authenticated HR API. It includes the standard seeded demo workflow when waiting for all provisioning jobs to reach terminal states. It never uses the frontend. Do not run campaigns concurrently under this project name.

Each invocation selects a fresh MongoDB volume with a random suffix and records its name in `config.json`. Retained volumes from earlier invocations do not block a repeated run identifier when its evidence directory is absent. Existing containers, evidence directories, and campaign volumes are never reused. Containers are stopped and removed on exit with Compose `down`; volumes are retained. Choose a new run identifier to preserve earlier evidence when repeating a campaign. No published ports are needed.

The run directory contains the exact invocation, environment versions, configuration, API creation manifest, read-only job snapshot, simulator accounts and statistics, applied faults, successful kill records, provisioner logs, and verification result. All measurements are generated by the run. Inspect `verify.json` for invariant failures and dead jobs whose simulator accounts exist and require an IT override. To repeat verification without services, run `python scripts/chaos/verify.py docs/evidence/chaos/<run-id>`.

Full campaign verification always requires replay, fence rejection, process kill, and committed-response-drop observations. Disabled or unexercised faults fail the campaign's `passed` result. Random fault injection may leave a required observation absent even when all jobs terminate correctly.

Disabling kills selects an explicit tooling dry run. The verifier still records all campaign failures and keeps `passed` false when fault coverage is missing. It additionally records `dry_run_passed`, which requires every job, account, and manifest invariant to pass. Only this explicit mode allows the runner to exit successfully despite missing fault observations; malformed evidence, data invariant failures, and command failures still produce a nonzero exit. A successful dry run cannot establish the full chaos claim. Repeat its tooling check offline by adding `--dry-run` to the verifier command; without that flag, verification always uses the strict campaign exit status.

This is a local demo on a single host. Accounts, payroll, identity, and devices are simulated; external systems are a local mock with injected faults. These runs make no production, high availability, or failover claim. The browser walkthrough remains manual.
